# 分支模型与开发流程

## 背景（现状与约束）

仓库只有一条无提交的 `master` 本地分支，远程 `origin` 没有任何分支。缺少分支约定时，功能改动容易直接落在主分支，也无法判断哪些分支可以安全删除。需要明确主分支、集成分支与临时分支的职责，并给出可执行的清理与合并步骤。

## 备选方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 只用 `master` | 无合并开销 | 主分支长期处于不可交付状态 |
| `master` + `develop` | 主分支稳定，功能集中集成，两层即可覆盖单人/小团队 | 多一次合并操作 |
| Git Flow 全量（`release/*`、`hotfix/*`） | 发布与热修流程分离 | 分支数量与维护成本对当前规模过高 |

## 决策

采用 `master` + `develop`：

- `master` 为唯一稳定基线与交付来源，只接受 `develop` 的合并。
- `develop` 承载全部功能开发，功能分支按需从 `develop` 切出并合回。
- 功能分支命名为 `feature/<描述>`，修复分支为 `fix/<描述>`，合并后删除。

## 理由

两层分支即可隔离不稳定改动与交付基线，无需发布分支；`develop` 作为唯一集成分支，避免出现多条并行集成分支导致结论分散。合并使用 `--no-ff` 保留开发过程，合并后立即在 `master` 重新验证，保证主分支始终可构建。

## 后果（影响与后续）

- 所有功能改动必须先经过 `develop`，`master` 上不允许直接提交功能代码。
- 分支清理前必须审计独有提交，删除远程分支属危险操作，需取得确认。
- 规则全文见仓库根目录 `AGENTS.md` 第 1–4 节。
- 待跟进：仓库尚无任何提交，`master` 基线需先建立，之后才能创建 `develop`。
